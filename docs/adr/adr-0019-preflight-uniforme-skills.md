# ADR-0019 — Preflight uniforme gerado nas skills a partir de `requires:`

- Status: aceito
- Data: 2026-07-25
- Origem: item 1 da Fase 2 do spec "Zero-friction onboarding — superfície Desktop/Cowork, export confiável e colapso da cadeia de instalação" (2026-07-22, aprovado); planejada em `docs/superpowers/plans/2026-07-24-zero-friction-fase2-golden-path.md`; evidência do spike da Fase 0 (`docs/superpowers/plans/archive/2026-07-23-zero-friction-fase0-spike-desktop-cowork.md`, verified 2026-07-24); precedente direto: ADR-0009 (blocos delimitados machine-owned)

## Contexto

O spike da Fase 0 — execução manual do dono no Claude Desktop/Cowork, 2026-07-24 — validou a premissa da instalação guiada (o Cowork executa comandos com consentimento na pasta designada) mas expôs três falhas concretas do estado sem contrato. Drift de versão silencioso: dentro de um `pj_*` recém-criado com `prumo init`, `prumo`/`uv run prumo` bare resolvem o CLI global stale da máquina (0.62.0) em vez da versão que o plugin espera, sintoma real capturado como `No such command 'verify-refs'`. Ausência de MCP invisível: os dois servidores declarados em `.mcp.json` (`qmd`, `prumo-review`) somem do inventário de tools da sessão sem erro nenhum em lugar nenhum — a persona jamais saberia que deveria existir busca semântica. Remediação de contexto errado: a orientação para estrutura de projeto ausente era `make new-project`, comando do monorepo do DONO — a persona (colega sem esse monorepo) não tem esse comando, e o caminho correto pós-PR#12 é `prumo init`. A decisão D1 do spec trava que operações exatas recusem com o comando de correção embutido, nunca simuladas pelo agente, que a skill ofereça instalar na hora com consentimento explícito, e que skills de julgamento puro (peer-review, scientific-writing) continuem funcionando sem CLI. Sem um contrato único, as 16 skills do plugin reimplementariam essa checagem em prosa livre por conta própria — divergindo com o tempo exatamente como os três achados acima já haviam divergido.

## Decisão

O preflight é um bloco Markdown machine-owned, delimitado por `<!-- prumo:preflight:begin -->`/`<!-- prumo:preflight:end -->`, estampado em cada `SKILL.md` pelo mesmo gerador que já mantém README/catálogo/índices (`.github/scripts/gen_indexes.py`) — nunca editado à mão. A fonte é um campo novo no frontmatter, `requires:` sob o bloco `prumo:`, parseado por `core/skills.py` (`SkillManifest.requires: tuple[str, ...] = ()`) contra os valores canônicos `VALID_REQUIRES = frozenset({"cli", "qmd", "zotero"})`; valor fora da lista levanta `ManifestError` citando os válidos, string única ou lista são aceitas, e repetições em `requires:` colapsam preservando ordem (`tuple(dict.fromkeys(requires))`) para o bloco gerado nunca duplicar item. O enforcement é `gen_indexes.py --check`, rodado no CI (`.github/workflows/ci.yml`), que falha listando qualquer `SKILL.md` dessincronizado da sua própria declaração de `requires:`.

A função `render_preflight(manifest)` compõe o corpo por classe presente em `requires`, renumerando os itens 1..N conforme o que se aplica. `cli` contribui três itens: existência do comando (`prumo --version`; ausente → não simular nenhuma operação da skill, rotear para `/prumo-assist:start` e parar ali); drift de versão via `$CLAUDE_PLUGIN_ROOT/.claude-plugin/plugin.json` comparado à versão do CLI, com fallback silencioso quando a variável não está definida (o item é simplesmente pulado, sem aviso, em superfícies que não a expõem); estrutura de projeto ausente → `prumo init pj_<nome>`, nunca scaffold manual nem tooling do monorepo do autor — fechando o achado de drift e o de remediação de contexto do Contexto acima. `qmd` contribui um item: tools MCP ausentes do inventário da sessão → dizer isso explicitamente e cair no fallback documentado pela própria skill, fechando o achado de MCP invisível; as três skills só-`qmd` sem `cli` (`wiki-query`, `wiki-ingest`, `active-learning`) herdam nesse mesmo item a frase de roteamento para `/prumo-assist:start` que o item de `cli` não está presente para prover. `zotero` contribui um item: `prumo doctor --json` → `external_deps[name=zotero].present`; ausente/fechado → recusa citando o hint do doctor. Skills com `requires: []` recebem a variante fixa (`_PREFLIGHT_PURE`): declaram que a skill não depende de CLI/Zotero/qmd, roda em qualquer superfície Claude, e não pode inventar dado de acervo/projeto — hoje `start`, `peer-review` e `scientific-writing`.

## Consequências

Toda skill nova PRECISA declarar `requires:` deliberadamente: o parser valida os valores presentes contra `VALID_REQUIRES`, mas não obriga o campo a existir nem a ser não-vazio — esquecer resulta, pelo default `()`, no bloco de julgamento-puro, o que não quebra `gen_indexes.py --check` e só fica visível a quem revisar o diff da skill nova. O bloco deixa de ser prosa livre por skill: qualquer ajuste de texto passa pelas constantes do gerador, nunca por edição direta de um `SKILL.md`, e o `--check` no CI garante que as 16 skills atuais não divirjam entre si com o tempo. A skill `start` vira o único caminho de instalação que este contrato reconhece — todo preflight que roteia por CLI ausente aponta para ela, nunca para instrução ad-hoc dentro da própria skill. O piloto da Fase 2 (item 4 do spec, gate externo do dono com 1 colega real, fora do escopo deste plano) mede esse contrato — não a implementação em si — no mundo real; o resultado calibra se e quando as Fases 4–5 (colapso de dependências, empacotamento do CLI) começam.
