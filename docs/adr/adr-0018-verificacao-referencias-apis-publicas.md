# ADR-0018 — Verificação de referências via APIs públicas, gate determinístico + enriquecimento opcional

- Status: aceito
- Data: 2026-07-24
- Origem: Fase 4 do spec "Round-trip de revisão docx ↔ CriticMarkup" (2026-07-05, aprovado), §"Camada de verificação de referências"; planejada em `docs/superpowers/plans/2026-07-24-ponte-fase4-verificacao-referencias.md`; spike 2026-07-24 (Crossref/PubMed/refchecker aterrados ao vivo); precedentes diretos: ADR-0007 (stdlib `urllib` para integração externa), ADR-0016/ADR-0017 (autoridade decrescente determinístico → agente)

## Contexto
O princípio de "zero erro silencioso de citação" cobria, até a Fase 3, a conservação e a identidade do campo Zotero dentro do próprio OOXML (ADR-0016) — mas nunca perguntava se a referência citada é real. A Fase 4 estende a garantia à própria referência: ela existe, não foi retratada, e é o que o `.bib` diz que é (spec, §"Camada de verificação de referências", itens 1–4). Isso muda a natureza do comando: é a primeira vez que um passo do CLI fala com a internet pública — toda integração externa até aqui era local (Zotero/Better BibTeX em `127.0.0.1:23119`, ADR-0007; `pandoc`; `uvx` para o `adeu` pinado no ingest de revisão), sem nenhuma chamada que saia da máquina do pesquisador.

## Decisão
`domains/paper/verify.py` implementa uma camada NATIVA determinística usando só `urllib` da stdlib (nenhuma dependência de runtime nova, mesmo racional do ADR-0007): existência e título via Crossref `GET works/{doi}` (`message.title[0]`, ou HTTP 404 se o DOI não resolve); retração via Crossref `GET works?filter=updates:{doi}&rows=5&select=DOI,update-to` (o próprio registro retratado não carrega `update-to` — quem carrega é a notice, em `message.items[].update-to[].type == "retraction"`); e retração por PMID via NCBI eutils `GET esummary.fcgi?db=pubmed&id={pmid}&retmode=json` (`result[pmid].pubtype` contendo `"Retracted Publication"`). Respostas boas ficam em `RefCache`, um JSON em `default_cache_path()` — `$XDG_CACHE_HOME/prumo-assist/refcheck.json`, fallback `~/.cache` quando a env var não está definida — com TTL de 7 dias; é o "cache local de retratações" do item 3 do spec. Um backend PROFUNDO opcional, acionado por `--deep`, roda `uvx academic-refchecker==3.0.151` (pinado, nunca flutuante — mesma disciplina do pin `adeu==1.29.0`) fora do processo Python, sobre um `.bib` reconstruído só com as entradas em escopo. Fato do spike 2026-07-24 que o seam (`_run_refchecker`) honra explicitamente: o refchecker termina com **exit 0 mesmo quando encontra erros** — sem chave de API o gate nunca pode ser o `returncode` do subprocess, só o `report.json` que ele escreve.

As três camadas têm autoridade decrescente. Achados nativos com `level="error"` (`retracted`, `doi-not-found`, `duplicate-citekey`, `network-error`) são o único gate do CLI — `verify_refs_command` levanta `typer.Exit(code=1)` quando `summary["errors"] > 0`, e só nesse caso. Achados do `--deep` viram sempre `level="warning"` (`_findings_from_report`) — enriquecimento, nunca gate, mesmo quando o refchecker aponta um problema grave. A skill `citation-support` (LLM) fica por cima de ambos, classifica se a citação sustenta a frase (Fully/Partially/Unsubstantiated) e só sinaliza no chat — nunca bloqueia comando, nunca edita arquivo. Três alternativas foram avaliadas e descartadas: baixar o dump completo do Retraction Watch (labs.crossref.org, 31 MB) — fica no backlog, fora do MVP, porque a consulta por-DOI acima já cobre o caso de citação individual; checar `doi.org` via HEAD antes do Crossref — redundante, já que o próprio `works/{doi}` responde 404 quando o DOI não resolve; e usar o refchecker como camada ÚNICA de verificação — rejeitado porque, sem chave de API, o pool compartilhado do Semantic Scholar é lento (504 e retries observados no spike) e, mais grave, seu exit code não serve como gate (fato acima), então o repo precisa de uma camada própria e determinística antes de qualquer enriquecimento externo opcional.

Privacidade por design: só DOIs/PMIDs saem da máquina na camada nativa — nunca título, abstract ou qualquer texto do manuscrito. O `--deep` envia apenas o subconjunto do `.bib` em escopo (`_bib_subset_text` reconstrói só as entradas citadas na página, nunca o `.bib` inteiro do acervo). O `User-Agent` (`prumo-assist/<versão> (+https://github.com/raphaelfh/prumo-assist)`) identifica o projeto sem carregar PII.

## Consequências
Offline, ou com a API fora do ar, cada entrada falha isolada com achado `network-error` (fail-soft por entrada, nunca exceção não tratada) — o restante do bib segue verificável e o comando continua determinístico mesmo com conectividade parcial. O item 2 do spec (Retraction Watch via Zotero) permanece responsabilidade do cliente Zotero, nativo e já disponível ao pesquisador; a checagem prumo acima é independente, cobre o `.bib` exportado, e não substitui nem duplica aquele aviso — as duas camadas coexistem. Custo permanente: o comando ganha uma superfície de rede que pode falhar ou ficar lenta (mitigada pelo cache de 7 dias e pelo escopo por página, recomendado sobre o bib inteiro) e uma segunda dependência de execução externa pinada (`uvx academic-refchecker==3.0.151`, ao lado de `adeu==1.29.0`) que não aparece em `pyproject.toml` por rodar fora do processo Python, mas exige a mesma disciplina de version-pin e o mesmo hint de instalação (`uv`) já estabelecidos para o `adeu`.
